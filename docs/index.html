The Problem: "ETL Hell"

Traditional data engineering tools (like AWS Glue or Nifi) were built for rows and columns. They choke on the unstructured chaos of the AI era.

The "Glue" Trap

  • The Thundering Herd: Sequential pipelines block on slow steps (like OCR), causing backpressure that halts the system.
  • The Kafka Bottleneck: Pushing heavy payloads (PDFs, Images) through brokers kills throughput and explodes retention costs.
  • Single-Model Lock-in: Changing chunking strategies or embedding models usually requires a full re-crawl and re-index.

The Pipestream Way

  • Reactive & Non-Blocking: Built on Quarkus and Mutiny. A single pod handles thousands of concurrent streams.
  • Claim-Check Pattern: Kafka carries the envelope (metadata). S3 & gRPC carry the heavy payload.
  • Multi-Vector Intelligence: Generate 5 embedding variations and 3 chunk sizes in a single pass, stored in one record.

Architecture Overview

The Document Hop

Pipestream operates on a "Document Hop" model. The Engine is the central router, moving PipeDocs (rich metadata envelopes) between specialized modules.

1. Data Loading

Assets are ingested via Connectors. Heavy data goes to S3; metadata goes to the Engine.

2. Transformation

Assets are transformed to text (Parsing). This step is skippable on "Rewind" operations.

3. Enhancement (Fan-Out)

Text is chunked and embedded. You can run multiple chunkers and embedders in parallel, accumulating results in the PipeDoc.

4. Sink

All accumulated vectors (from all strategies) are indexed into OpenSearch or PostgreSQL for hybrid retrieval.
