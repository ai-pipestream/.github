⚡ Dual-Mode Transport

Why choose between speed and scale? Pipestream routes high-priority UI requests via gRPC (milliseconds) and bulk ingestion via Kafka (terabytes). The engine handles the switching dynamically.

🌐 Polyglot Service Mesh

Write LLM logic in Python. Write parsers in Rust or Java. Connect them seamlessly. Modules are "dumb" gRPC endpoints; the Engine handles the complex orchestration, retries, and state.

🛡️ Schema-First Governance

Prevent data corruption. We use Protobuf and Apicurio Registry to enforce strict data contracts. The Engine controls the mapping, so a rogue script can never break your Search Index.

How It Works: The Engineering Flow

Pipestream separates the control plane from the data plane to handle massive files without clogging your message broker.

1. Ingest & Claim Check

The Intake Service accepts a document. Large binaries (PDFs) are immediately offloaded to S3 (Repo Service). Only the lightweight PipeDoc metadata enters the stream.

2. The Engine Router

The Engine receives the PipeDoc. Based on priority, it routes via gRPC to the next Node, or pushes a pointer to the pipeline-work-v1 Kafka topic if the node is busy.

3. Polyglot Processing

Your Python Summarizer Module receives a typed Request. It pulls text, runs the LLM, and returns the result. It never touches S3 or Kafka directly.

4. Strict Indexing

The Engine takes the result, applies strict schema mapping (so "summary" goes to "metadata.description"), and indexes it into OpenSearch safely.
